# 迭代记录

约定：调规则 / 提示词**只看 dev 集**（20 条），规则冻结后才跑 **test 集**（10 条）报告结果。
以下数字都是 `python evals/run_eval.py --no-llm` 实际跑出来的（mock 模式，只评规则部分）。

## 迭代 1：规则 v1 → v2（2026-11-13）

### 现象（v1，dev）
| 指标 | 结果 |
| --- | --- |
| 准确率 | 40% |
| 规则覆盖率 | 35% |
| 规则精确率 | 100% |

12 条判错 / 未判出，全部是规则没认出来（交给 mock，判成「无法判断」），**没有一条是规则判错**。

### 原因判断
把 12 条失败分成两类：
1. **同义写法，意思明确（9 条）**：`timed out`、`超时`、`watchdog`、`看门狗`、`brown-out`、`under-voltage`、
   `did not acknowledge`、`No ACK`、`pogo pin / jig` —— v1 只写了最标准的关键词（timeout、WDT、NACK…）。
2. **需要理解语义（3 条）**：
   - D17「Expected 3 LED blinks, observed 1」、D18「baseline drifted」：行为与期望不符，但没有固定关键词。
   - D19「Device rebooted unexpectedly」：**可能是看门狗，也可能是掉电**，写成规则有判错风险。

### 修改
- 第 1 类：在 `rules.py` 补充同义写法（含中文、连字符变体），并在 `tests/test_rules.py` 为每种写法加用例。
- 第 2 类：**故意不写规则**，交给 LLM；并加测试 `test_ambiguous_reboot_is_left_to_llm` 锁住这个决定。
- 关键词按整词匹配（如 `\bjig\b`），加测试防止「jiggle」这类误伤。

### 结果
| 集合 | 版本 | 准确率 | 规则覆盖率 | 规则精确率 |
| --- | --- | --- | --- | --- |
| dev | v1 | 40% | 35% | 100% |
| dev | v2 | **85%** | 80% | 100% |
| test | v1 | 50% | 50% | 100% |
| test | v2 | **90%** | 90% | 100% |

- 规则精确率保持 100%：规则只「少判」，不「判错」。CI 用 `--min-rule-precision 1.0` 守住这条底线。
- 剩下未判出的 D17、D18、D19、X10 都属于第 2 类，是 LLM 该处理的部分。
- 副作用：`tests/test_llm.py` 有一个用例原本用「Brown-out」当作规则认不出的例子，v2 后规则能认出，
  改用真正模糊的「意外重启」。**回归测试及时发现了这个行为变化。**

### 这组数字的局限
- 评测集只有 30 条，test 只有 10 条，一条就是 10 个百分点。
- 题目和规则是同一个人写的，test 集可能偏向规则能覆盖的写法 → 需要真实产线日志，最好由测试工程师标注。
- 标准答案（例如 D19 算看门狗）是我的判断，需要领域专家确认。
- 以上只评了**规则**；LLM 部分要配置 API key 后再跑（见迭代 2）。
